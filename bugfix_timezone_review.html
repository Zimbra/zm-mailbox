Timezone Handling Review for Sieve Filter Parsing

Summary

The issue was caused by timezone handling being attached to a shared DateParser instance used for filter parsing and formatting. When the timezone was null or empty, the code hit a NullPointerException. The fix was updated to make timezone handling explicit and local to each conversion operation, avoiding shared mutable state.

Root Cause

  • PR 1542 introduced timezone state into DateParser.
  • The shared Sieve.DATE_PARSER instance was then reused across filter conversions.
  • When a timezone value was missing, TimeZone.getTimeZone(null) led to an exception.
  • The mutable timezone state also risked leaking between requests or conversions.

Why the Original Fix Was Risky

The earlier approach set the timezone on a globally shared parser object. That is problematic because it introduces shared mutable state into a component that is reused by multiple filter operations.

  • Potential cross-request contamination
  • Possible concurrency hazards
  • Hidden state that is hard to reason about

Better Fix Approach

The safer fix is to keep timezone handling explicit and local to each parse/format operation.

parse(String value, String timezone)
format(Date value, String timezone)

This avoids stale shared state and handles null/empty timezone values by falling back to the JVM default timezone.

Implemented Changes

  • Updated DateParser with overloads for explicit timezone usage.
  • Changed Sieve conversion to pass the account timezone explicitly.
  • Propagated timezone through the filter visitor so date comparisons are parsed with the correct zone.
  • Added regression tests for null/explicit timezone handling.
